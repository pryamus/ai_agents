Потенциальные проблемы уже видны на уровне архитектуры: при росте нагрузки приложение будет упираться в синхронный SQLAlchemy-сессию, один SQLite/один процесс и отсутствие ограничений на количество запросов. Сейчас коротко перечислю самые важные риски и как обычно их решают.

## Потенциальные проблемы на уровне архитектуры при росте количества запросов

### 1. Синхронная работа с БД
В проекте используются обычные синхронные ORM-сессии через SQLAlchemy и FastAPI-обработчики.

Проблема:
- при росте числа одновременных запросов один worker будет держать больше I/O-операций
- увеличивается время ответа
- если запросов много, может начаться очередь на обработку

Что обычно делают:
- перейти на асинхронный access layer
- использовать async SQLAlchemy или отдельный сервисный слой
- увеличить число workers / uvicorn workers
- вынести DB-операции в пул соединений

---

### 2. SQLite не подходит для высокой нагрузки
В production по умолчанию используется SQLite, а это хорошо для локальной разработки и учебного проекта, но не для высокой нагрузки.

Проблема:
- ограниченная конкурентность
- блокировки на запись
- медленная работа при большом числе параллельных запросов
- рост latency под нагрузкой

Что обычно делают:
- заменить на PostgreSQL
- использовать транзакции и правильный пул соединений
- вынести БД в отдельный сервис

---

### 3. Нет ограничения на нагрузку и ресурсы
В API нет:
- rate limiting
- ограничений на размер запроса
- таймаутов
- контроля очередей

Проблема:
- один клиент может забить сервис
- вырастает число запросов к БД
- начинается деградация по памяти и CPU

Что обычно делают:
- ограничивать число запросов по IP / user
- ставить rate limiting
- ограничивать размер payload
- использовать reverse proxy / gateway

---

### 4. Прямой доступ к CRUD из роутеров
Сейчас маршруты вызывают CRUD напрямую и это нормально для учебного проекта, но на росте масштаба это создаёт проблемы:

Проблемы:
- логика смешивается с HTTP-слоем
- сложнее добавить валидацию, кэш, транзакции, аудит
- тяжело масштабировать бизнес-логику

Что обычно делают:
- сервисный слой:
  - TicketService
  - validation
  - business rules
  - transaction boundaries
- роутеры только принимают HTTP и делегируют

---

### 5. Отсутствие кэширования
Если много одинаковых запросов на список тикетов или чтение одного и того же тикета, можно перегружать БД.

Проблемы:
- одинаковые запросы повторяются
- лишняя нагрузка на SQL
- рост задержки

Что обычно делают:
- кэшировать частые ответы
- использовать Redis
- кешировать чтения, но не критичные изменяемые данные

---

### 6. Нет мониторинга и метрик
При росте нагрузки без наблюдения нельзя понять:
- где bottleneck
- сколько времени занимает SQL
- какие endpoints ломаются
- какие запросы самые дорогие

Что обычно делают:
- Prometheus / Grafana
- структурированные логи
- трассировка запросов
- метрики по DB latency, HTTP latency, error rate

---

### 7. Невозможность горизонтального масштабирования
Сегодня это скорее монолит с одной БД и одним приложением.

Проблема:
- сложно масштабировать по нескольким экземплярам сервиса
- возникают race conditions, синхронизация данных
- при нескольких инстансах локальные файлы/локальные ресурсы становятся проблемой

Что обычно делают:
- отдельный внешний DB
- stateless app
- горизонтальное масштабирование через контейнеры / k8s
- Redis / message queue для async задач

---

### 8. Возможные проблемы с конкурентной записью
Если несколько клиентов одновременно создают или меняют тикеты, без корректной логики транзакций можно получить:
- lost update
- некорректное состояние тикета
- гонки между запросами

Что обычно делают:
- проверять версии записей
- использовать optimistic locking / row versioning
- контролировать транзакции

---

## Краткий вывод
Для учебного проекта это нормально, но при росте нагрузки архитектура начнёт ограничивать:
- SQLite
- синхронные SQLAlchemy сессии
- отсутствие rate limiting
- отсутствие кэша
- отсутствие сервисного слоя
- отсутствие наблюдаемости

Самый важный следующий шаг:
- заменить SQLite на PostgreSQL
- перейти на асинхронный слой или хотя бы увеличить пул workers
- добавить мониторинг и ограничение нагрузки
