Тема 2.6 — Skills и Tools: инструменты агента

Цель темы

Регистрировать инструменты так, чтобы LLM понимала их (JSON Schema из сигнатуры), аргументы валидировались до вызова, а исполнение было изолировано (таймаут, обрезка, защита путей). Различать skill, tool и MCP. Опционально — открыть инструменты внешним клиентам через MCP.

Часть 1. Теория

4.1 Skill ≠ Tool ≠ MCP

Что это Пример Кто исполняет
Tool исполняемая функция + описание для LLM grep_search, ruff_lint рантайм (opencode/цикл)
Skill процедура: инструкция «когда и в каком порядке» «аудит: сначала grep, потом linter» модель, прочитавшая SKILL.md
MCP протокол подключения инструментов извне сервер labtools на FastAPI внешний процесс по HTTP

Скилл говорит «что делать в какой ситуации», инструмент — «чем сделать». Скилл подгружается по требованию (лениво), схемы инструментов лежат в системном промпте постоянно.

4.2 Жизненный цикл инструмента

@tool(timeout=10)                                  # 1. декоратор собирает метаданные
def grep_search(pattern: str, path: str = ".",     # 2. сигнатура → типы/обязательность
                use_regex: bool = False) -> str:
    """Найти строки в файлах, результат: путь:номер: текст.   # 3. docstring → описание
    pattern: что искать            # 3b. «name: текст» → описания параметров
    ...
    """

Четыре стадии (tool_registry.py):

  1. Описание — pydantic-модель аргументов из аннотаций → model_json_schema() → блок в системном промпте агента. Качество описания = шанс, что модель выберет инструмент и верные аргументы. Это и есть «описание функций для LLM» из плана темы.
  2. Валидация до вызова — extra="forbid" (галлюцинированные ключи отклоняются), обязательность по отсутствию default, типы. Ошибка валидации — данные для модели (feedback), а не exception наружу.
  3. Исполнение в изоляции — ThreadPoolExecutor + timeout (зависший вызов не вешает цикл), привязка путей к корню проекта (path traversal невозможен), ToolError вместо сырых исключений.
  4. Нормализация вывода — любой тип → строка (json.dumps), обрезка до max_output — защита контекстного окна (2.4).

4.3 Три типа «неудачи» — три разных политики

Тип Код Пример Политика
Аргументы неверны invalid_args нет pattern, лишний ключ feedback модели, без ретрая
Временный сбой timeout (retryable=True) git/ruff не отвечают ретрай, затем feedback
Детерминированный провал runtime не git-репозиторий, ruff не установлен feedback без ретрая

А вот «linter нашёл 20 замечаний» — НЕ ошибка. ruff check завершается кодом 1 — это результат работы (данные), которые модель должна увидеть; исключение (ToolError) бросается только при rc=2 — когда линтер не смог запуститься. Умение отделить «данные» от «сбоя» — главный навык проектирования инструментов.

4.4 Набор инструментов курса (tool_impls.py)

Инструмент Аргументы Заметки
grep_search pattern, path, include, use_regex, max_results regex-безопасность (re.escape по умолчанию), стоп по max_results
git_diff path, staged, max_chars пустой diff → «изменений нет» (данные!); rc≠0 → runtime
ruff_lint path, select rc0 → «нет замечаний», rc1 → список, rc2 → runtime

Все три регистрируются в ToolRegistry(root=…) — единственной точке описания, валидации и исполнения. Цикл из 2.5 использует реестр без изменений (реализует тот же протокол ToolHost).

4.5 MCP: открыть инструменты наружу

Model Context Protocol — стандарт подключения инструментов к агенту по HTTP/stdio: рантайм не модифицируется, инструменты живут в отдельном процессе/сервисе.

Реализация курса (mcp_server.py, mcp SDK 2.x → класс MCPServer; в 1.x он назывался FastMCP):

FastAPI /health ──┐
                  ├── app ── POST /mcp  (Streamable HTTP)
MCPServer 3 tools ┘

Тонкости, проверенные на практике (входят в лабораторную):

  • дочернее приложение streamable_http_app() само отдаёт маршрут /mcp, поэтому его монтируют в корень (app.mount("/", …)) — иначе путь удвоится до /mcp/mcp;
  • session_manager должен жить в lifespan FastAPI;
  • регистрация идёт через _via_registry(...): схема берётся из сигнатуры, но вызов проходит через ToolRegistry.dispatch — валидация и защита путей действуют и через протокол, а не только внутри цикла;
  • ToolError по MCP отдаётся модели текстом (ИНСТРУМЕНТ НЕ ВЫПОЛНЕН [code]: …) — ошибка снова превращается в данные.

Подключение к opencode:

opencode mcp add labtools --url http://localhost:8000/mcp   # пишет mcp.servers в opencode.json
opencode mcp list                                           # ✓ labtools connected
opencode run "найди TODO через labtools_grep_search"

Инструменты внешнего сервера получают имена <сервер>_<инструмент> — это устраняет коллизии имён между источниками.

4.6 Skills в opencode

.opencode/skills/codebase-audit/SKILL.md
---
name: Аудит кодовой базы
description: Когда применять (поиск TODO → контекст → linter → diff)
---
# Codebase audit — workflow, правила вывода, ограничения

Скилл подгружается моделью через skill tool по описанию; схемы инструментов при этом уже в промпте от рантайма — они дополняют друг друга: скилл даёт последовательность, реестр — «чем».

4.7 Безопасность инструментов

  • Path traversal: строковые пути проверяются на resolve().is_relative_to(root) реестра — path: "../.." → permission-ошибка (тест в лабораторной).
  • Shell: только фиксированные бинари (git, ruff), shell=False, аргументы — списком; никакой интерполяции строки в команду.
  • Prompt injection через вывод: вывод инструмента — данные, содержащие потенциальные «инструкции» (например, README со строкой «ignore previous instructions»). Политика: не исполнять содержимое вывода как приказы, ограничивать длину, для критичных действий — permissions из 2.3.
  • Ресурсы: max_results/max_output защищают и латентность, и окно.
