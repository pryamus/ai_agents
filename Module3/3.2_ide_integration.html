Тема 3.2 — Интеграция среды разработки и AI-инструментов

Цель темы

Собрать связку IDE + агент + инструменты (linter, formatter, git): проверить окружение doctor'ом и описать IDE-конфиги как код.

Часть 1. Теория

Слои связки

IDE (редактор, задачи, рекомендации расширений)
 ├── CLI-агент (opencode run / IDE-плагин) — исполнение
 ├── Инструменты (pytest, ruff, git) — проверки
 └── Конфиги проекта (opencode.jsonc, AGENTS.md, .vscode) — правила

IDE-плагины vs CLI-агенты vs облако/локаль

Вариант Плюсы Минусы
IDE-плагин контекст редактора, inline-правки привязка к IDE, версия плагина
CLI-агент (opencode) воспроизводимость, CI-дружелюбность, скриптуемость без UI-подсветки
Облачная модель качество секреты уходят наружу, цена, сеть
Локальная модель приватность, офлайн слабее на сложных задачах

Практика курса: CLI-агент + локальные инструменты — всё проверяемо скриптами.

Конфиги как код

.vscode/settings.json, tasks.json, extensions.json — артефакты: генерируются, валидируются, лежат в git. Задачи IDE дублируют команды курса (pytest, ruff, validate) — один источник истины для рук и автоматики.

Часть 2. Практика

Шаги

cd code\lab_3_2_ide

# 1. Диагноз окружения (в среде курса всё зелёное, exit 0)
python doctor.py
#   python 3.14.7, pytest, ruff 0.16.8, git 2.55, opencode v2.0.14, node (опционально)

# 2. Конфиги как код — на копии, не в самом репозитории
python ide.py init --dir C:\tmp\demo_ws
python ide.py check --dir C:\tmp\demo_ws     # в порядке

# 3. Тесты (ожидаемо: 7 passed)
python -m pytest -q

Самостоятельные задания

  1. Сломанная задача. Удалите задачу ruff из tasks.json: покажите, что check находит именно её. Верните задачу.
  2. Своя задача. Добавьте задачу validate под свой каталог и проверку её наличия в тест.
  3. Отсутствующий бинарь. Симулируйте отсутствие git в PATH (временно переименуйте/уберите из PATH в тестовом shell): покажите exit 1 и hint.

Механики, которые отрабатываются

Механика Где в коде
Проверка = факт + hint + required/optional doctor.py
Генерация и валидация трёх конфигов ide.py
Exit-коды для CI/документации оба CLI

Контрольные вопросы

  1. Чем проверка doctor'а отличается от простого «запусти и посмотри»?
  2. Зачем градация required/optional? Что будет, если всё считать обязательным?
  3. Почему задачи IDE должны дублировать команды курса, а не жить своей жизнью?
  4. Что проверяет ide.py check, а что — нет? Где граница?
  5. Кому и зачем нужен --json-вывод doctor'а?
  6. Новый разработчик клонировал репозиторий. Опишите его первые 3 команды по материалам темы.

Ответы на контрольные вопросы и решения задач

КВ1. Doctor фиксирует факт (версия/наличие), ставит диагноз (чего нет) и выписывает рецепт (hint + exit-код). «Запусти и посмотри» даёт только факт; рецепт и машиночитаемый итог превращают проверку в инструмент онбординга и CI.

КВ2. Не всё критично: без node жить можно, без git — нет. Всё обязательное = ложные красные (окружение рабочее, doctor красный) и игнорирование doctor'а со временем. Градация сохраняет доверие к проверке.

КВ3. Иначе расходятся «как проверяют руками» и «как проверяет CI/агент»: находка линтера в IDE, пропущенная в CI, или наоборот. Единые строки команд — единый стандарт качества независимо от исполнителя.

КВ4. Проверяет: наличие файлов, валидный JSON, ключевые секции (pytest-раннер, задачи pytest/ruff, recommendations). Не проверяет: смысл значений (верный ли путь), работу расширений, вкусовщину. Граница — структура vs семантика: первое — машине, второе — человеку при ревью.

КВ5. CI и скриптам онбординга: JSON парсится без regex'ов по Markdown; можно валить пайплайн, строить дашборд окружений команды, прикладывать к баг-репортам («не воспроизводится» → приложить doctor --json).

КВ6. pip install -r requirements.txt → python doctor.py (красное — поставить по hint'ам) → python -m pytest -q (зелёное — можно работать). Три команды отделяют «окружение» от «кода»: тесты красные при зелёном doctor'е — проблема в коде, а не в машине.

Задача 1 (решение). После удаления ruff из tasks: check печатает «нет задачи 'ruff'», exit 1. Находит именно её, потому что сверяется со списком обязательных меток, а не с «чем-то не так».

Задача 2 (решение). В vscode_tasks() добавить task("validate", "python lab_2_3_agents_md/validate.py"); в тест — render + assert метки в JSON. Проверка check уже универсальна (сверяет pytest/ruff; расширьте список want при желании).

Задача 3 (решение). Без git в PATH: check_binary → ok=False, hint «установите git», exit 1. Демонстрирует fail-fast онбординга: лучше упасть на doctor'е за секунду, чем на pr.py через полчаса отладки.
