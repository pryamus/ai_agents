Тема 2.4 — Контекстное окно и память агента (RAG)

Цель темы

Понять, из чего состоит контекстное окно LLM, какие стратегии управления памятью существуют, и собрать рабочий RAG-пайплайн: индексация кодовой базы → векторный поиск → упаковка контекста под бюджет токенов → передача модели.

Часть 1. Теория

2.1 Контекстное окно: что туда попадает

┌───────────── контекстное окно (context window) ──────────────┐
│ system prompt (роль + инструкции + описания инструментов)    │
│ история диалога / сообщения цикла (шаги, выводы инструментов)│
│ найденный контекст (RAG)                                     │
│ текущий запрос пользователя                                  │
└──────────────────────────────────────────────────────────────┘
  • Окно измеряется в токенах, не в символах: токенизатор зависит от модели (≈3–4 символа русского текста на токен у BPE-токенизаторов).
  • Окно ограничено и платно: платится за каждый токен входа, а длина ответа ограничена max_tokens.
  • Практика курса использует грубую оценку approx_tokens = ceil(len/4) (см. shared/llm.py) — достаточно для бюджетирования, точность не критична.

2.2 Стратегии управления памятью

Стратегия Идея Плюсы Минусы
Truncation отрезать старое/хвост дёшево, просто теряется контекст
Summarization сворачивать старое в саммари держит суть стоимость вызовов, искажения
Compaction по завершении «сжимать» прогон в заметку (план+выводы) хорошо для многошаговых задач логика на рантайме
Long context просто увеличить окно без инфраструктуры квадратичный attention, цена, «lost in the middle»
RAG хранить всё снаружи, в окно — только релевантное масштабируемо, дёшево, цитируемо нужен индекс и оценка качества

RAG (Retrieval-Augmented Generation) — основная стратегия для знаний о коде/документации: храним векторный индекс, в промпт кладём топ-k релевантных фрагментов, уложившихся в бюджет.

2.3 Пайплайн RAG (по нему устроена лабораторная)

файлы ──чанкинг──▶ чанки ──эмбеддинг──▶ векторы ──▶ VectorIndex
                                                       │
вопрос ──▶ вектор вопроса ──cosine top-k──▶ хиты ──pack_context(бюджет)──▶ промпт ──▶ LLM

1) Чанкинг (chunker.py) — нарезка с сохранением семантических границ:

  • Python: ast — чанк = функция/класс/модульный докстринг;
  • Markdown: заголовки (иерархия документа);
  • Всё прочее: строки окнами с overlap (перекрытие), чтобы разрез не терял связку «объявление — продолжение».

Целевой размер ≈300–1200 символов: достаточно контекста для понимания фрагмента, мало enough, чтобы несколько фрагментов влезали в бюджет.

2) Эмбеддинг (embedders.py) — единый интерфейс encode(texts) → матрица L2-нормированных векторов, две реализации:

TfidfEmbedder MiniLMEmbedder (BERT)
Принцип слово ↔ вес, подсчёт совпадений transformer, смысл фрагмента
Размерность тысячи (разреженный TF-IDF → dense) 384
Смысл синонимов не понимает («скидка» ≠ «скидки») понимает
Зависимости scikit-learn sentence-transformers (~470 МБ)
Роль в курсе офлайн-фолбэк, детерминизм «BERT-вариант» по ТСП

Модель курса: paraphrase-multilingual-MiniLM-L12-v2 — мультиязычная, кроссъязычная: cosine(«агент ограничивает число шагов», «agent limits the number of steps») ≈ 0.965 (проверено прогоном). make_embedder("auto") берёт MiniLM, а при недоступности — TF-IDF (EmbedderError не роняет сервис).

3) Индекс (index.py) — плоский (flat) индекс на numpy:

  • search(query, k): вектор запроса → косинусное сходство со всеми → топ-k. За O(n·d) — приемлемо для тысяч чанков; для миллионов нужны ANN-структуры (HNSW/IVF) — вопрос для самостоятельного изучения.
  • save/load: vectors.npy + chunks.json + meta.json. Смена эмбеддера без переиндексации — ошибка: векторы разных моделей живут в разных пространствах (тест ловит несовместимость по имени).
  • У TF-IDF состояние обученное (векторайзер) — поэтому save_state сохраняет его в индекс, иначе восстановленный индекс не умел бы кодировать запросы.

4) Упаковка под бюджет (context.py → pack_context):

  • хиты сортируются по релевантности, в промпт попадают по убыванию score, пока хватает бюджета токенов;
  • каждый фрагмент снабжается путь:строки — атрибуцией, без неё модель не может сослаться на источник;
  • релевантный, но слишком длинный фрагмент отбрасывается — окно ограничено, бюджет важнее полноты.

2.4 Оценка качества RAG

  • recall@k — доля запросов, для которых нужный файл попал в топ-k (метрика retrieval, считается без LLM);
  • качество ответа (по контексту) — отдельно: точность цитат, полнота;
  • латентность: TF-IDF ≈ единицы мс, MiniLM ≈ десятки–сотни мс на батч;
  • типичная диаграмма компромисса: больше k → recall ↑, бюджет и латентность ↑.

2.5 Ограничения и риски

  • Свежесть: индекс надо переиндексировать при изменении файлов (в курсе — ручной POST /index; в проде — вебхуки/патчи).
  • Prompt injection через найденный текст: файл может содержать «инструкции для модели» — контекст из retrieval нужно помечать как данные, а не как приказы (тема безопасности 2.6).
  • Хранение: у TF-IDF размерность словаря, у MiniLM — 384·4 байта на чанк.

Часть 2. Практика

Шаги

cd M2_rag/code

# 1. CLI-демо без сервера (офлайн, TF-IDF): индексация курса → top-k → промпт
python rag_demo.py --embedder tfidf --query "как ограничить число шагов агента" --k 3
#    ожидаемо: «N файлов -> M чанков», список хитов с оценками,
#    собранный промпт в рамках --budget 2000

# 2. Сохранить/загрузить индекс (персистентность, включая векторайзер TF-IDF)
python rag_demo.py --embedder tfidf --save index_cache --query "права агента"
python rag_demo.py --load index_cache --query "права агента"

# 3. BERT-вариант (скачается модель ~470 МБ один раз)
pip install sentence-transformers
python rag_demo.py --embedder minilm --query "падения и исключения инструментов"
# сравнить с tfidf на запросе-синониме: смысл найдётся только у minilm

# 4. FastAPI-сервис
uvicorn api:app --reload                 # отдельный терминал
curl -X POST localhost:8000/index  -H "Content-Type: application/json" -d '{"embedder":"tfidf"}'
curl -X POST localhost:8000/search -H "Content-Type: application/json" -d '{"query":"роли агентов","k":3}'
curl -X POST localhost:8000/ask    -H "Content-Type: application/json" -d '{"question":"из чего состоит манифест агента"}'
curl localhost:8000/health              # indexed / chunks / embedder

# 5. Тесты (ожидаемо: 13 passed)
python -m pytest -q

Самостоятельное задание: замерить recall@3

  1. Возьмите 5 вопросов с известным ответом (файл:строка).
  2. Для каждого запроса POST /search с k=3: попал ли нужный файл в топ-3.
  3. Посчитайте recall@3 для tfidf и minilm, сравните. Пример вопросов: «где определены права агента?», «сколько шагов по умолчанию у цикла?».
  4. Сформулируйте вывод: где TF-IDF достаточен, а где обязателен эмбеддинг.
